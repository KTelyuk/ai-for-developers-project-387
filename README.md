# Календарь звонков

[![hexlet-check](https://github.com/KTelyuk/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/KTelyuk/ai-for-developers-project-387/actions)

Продолжение проекта [ai-for-developers-project-386](https://github.com/KTelyuk/ai-for-developers-project-386): история коммитов перенесена, ссылки на старые issues ведут туда.

Сервис для бронирования времени звонка, разработанный совместно с ИИ.

**Демо:** https://ai-for-developers-project-387-05lg.onrender.com (бесплатный тариф Render: первый запрос после простоя может идти до минуты, данные при этом сбрасываются).

## Сценарий

«Запись на звонок» — упрощённый сервис бронирования по мотивам [Cal.com](https://cal.com/). Владелец календаря один и задан заранее, гость записывается без регистрации.

1. **Владелец создаёт тип встречи** в разделе `/admin`: указывает название, описание и длительность (например, «Знакомство», 30 мин).
2. **Гость открывает сервис** и выбирает тип встречи из списка.
3. **Гость выбирает день** в календаре на ближайшие 14 дней. У каждого дня видно, сколько на нём свободных слотов; выходные недоступны.
4. **Гость выбирает время.** Слот длится столько, сколько выбранный тип встречи; занятые интервалы недоступны.
5. **Гость вводит имя и email** и подтверждает запись. Если время успели занять, сервис сообщает о конфликте и предлагает выбрать другой слот.
6. **Гость получает ссылку на свою запись.** На экране подтверждения есть подсказка «Сохраните ссылку — без неё запись не отменить» и кнопка «Скопировать».
7. **Запись появляется у владельца** в списке предстоящих встреч (все типы вместе, по времени начала).
8. **Запись можно отменить.** Гость отменяет её по своей ссылке, владелец — кнопкой «Отменить» в своём списке. Отменённая встреча удаляется, а её время снова становится свободным.
9. **Гость может изменить запись.** По своей ссылке гость кнопкой «Изменить» выбирает другой тип встречи, день и время, правит имя и email. Ссылка остаётся прежней, а старое время освобождается только после того, как занято новое.

### Роли

- **Владелец** работает в разделе `/admin`. На этом этапе раздел открыт без авторизации: владелец один, а защита входом в задание не входит.
- **Гость** видит только интерфейс записи и страницу своей записи по ссылке. Ссылок на `/admin`, чужих записей, имён и email других гостей в гостевом интерфейсе нет.

### Обязательные функции

- Владелец: создание и редактирование типов встреч (название, описание, длительность), просмотр предстоящих встреч всех типов, отмена любой записи. Удаления типов встреч пока нет.
- Гость: выбор типа встречи, календарь свободных слотов на 14 дней, бронирование с именем и email, изменение и отмена своей записи.
- API описан контрактом на TypeSpec, из него генерируется OpenAPI-спецификация, а из неё — клиентский SDK для фронтенда.
- Приложение собирается в Docker-образ и запускается в контейнере.

### Правила и ограничения

- Окно записи — 14 календарных дней, сдвигается вместе с текущей датой.
- Одно и то же время нельзя занять дважды, даже разными типами встреч; частичное пересечение тоже запрещено.
- Следующая встреча может начинаться ровно в момент окончания предыдущей.
- Правила соблюдаются и для одновременных запросов.
- Гость может отменить запись, только если у него есть ссылка на неё: ссылка содержит секретный токен, который выдаётся при бронировании. Встречу, которая уже началась, нельзя ни отменить, ни изменить.
- Отменённая запись удаляется. Повторная отмена или открытие её ссылки возвращает `404`.
- Изменение длительности типа встречи не затрагивает уже созданные записи: они сохраняют своё время начала и окончания. Новая длительность действует для новых записей.
- Нет авторизации, личных кабинетов, интеграций с внешними календарями и уведомлений.
- Интерфейс только на русском языке.
- **Данные хранятся в памяти процесса.** Перезапуск приложения стирает все типы встреч и записи. На бесплатном тарифе Render сервис засыпает после простоя, и при пробуждении данные тоже пропадают; демо при каждом старте заново создаёт три типа встреч (переменная `SEED=true`). В режиме разработки (`mise run dev`) бэкенд перезапускается при каждом изменении кода и стартует с тремя заготовленными типами встреч, чтобы не создавать их заново.

### Параметры расписания

| Параметр                  | Значение                                                                                                                                                 |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Часовой пояс              | Алматы, Казахстан (`Asia/Almaty`, UTC+5). Всё время в интерфейсе показывается в нём                                                                      |
| Рабочие дни               | Понедельник — пятница. Суббота и воскресенье нерабочие                                                                                                   |

| Шаг стартов               | 15 минут (09:00, 09:15, 09:30…)                                                                                                                          |
| Длительность типа встречи | Выбор из списка: 15, 30, 45 или 60 минут                                                                                                                 |

### Устройства

Сервисом пользуются и на компьютере, и на телефоне: интерфейс адаптивный, все сценарии гостя и владельца доступны на любом экране.

- **ПК (от 1024 px):** раскладка как на макетах — информация, календарь и слоты в три колонки рядом.
- **Планшет (768–1023 px):** календарь и слоты в две колонки, блок «Информация» над ними.
- **Телефон (от 360 px):** все блоки идут друг под другом в порядке шагов: тип встречи → календарь → слоты → форма. Кнопки «Назад» и «Продолжить» закреплены внизу экрана.
- Элементы, на которые нажимают пальцем (дни календаря, слоты, кнопки), — не меньше 44 × 44 px.
- Поле email открывает на телефоне клавиатуру с `@`.
- Горизонтальной прокрутки страницы нет ни на одном размере экрана.

Адаптивность проверяется e2e-тестами Playwright на двух профилях: десктоп (1280 × 800) и телефон (эмуляция iPhone и Android).

## Тестирование

Каждый модуль покрыт тестами. Тесты пишутся вместе с кодом в каждом тикете; тикет считается готовым, только когда его тесты проходят.

### Шаги

1. **Контракт (TypeSpec → OpenAPI).** Контракт компилируется без ошибок и предупреждений. `mise run check-generated` повторяет генерацию OpenAPI, SDK фронтенда и типов бэкенда и сверяет их с закоммиченными: если контракт изменили, а код не перегенерировали, или сгенерированное правили вручную, проверка падает.
2. **Клиентский SDK.** SDK генерируется из актуальной спецификации, после этого фронтенд проходит проверку типов. Расхождение контракта и кода фронтенда ловится на этапе сборки.
3. **Бэкенд: доменная логика (unit-тесты).**
   - Генерация слотов: часы работы, обед 13:00–14:00 (встреча не начинается и не заканчивается внутри него), выходные, шаг стартов, длительность типа встречи, окно 14 дней, часовой пояс Алматы, прошедшее время недоступно.
   - Пересечения: точное совпадение, частичное наложение, вложенный интервал, разные типы встреч, встреча впритык к предыдущей разрешена. Встречи разной длительности: 60 минут в 10:00 и 30 минут в 10:30, 09:45 или 10:45 — `409`.
   - Отмена гостем: верный токен, неверный токен, уже начавшаяся встреча, повторная отмена (`404`).
   - Изменение гостем: новые тип, время и данные; неверный токен; уже начавшаяся встреча; занятое и недопустимое время; сдвиг на время, перекрывающее прежнее.
   - Отмена владельцем: запись удаляется, время освобождается.
   - Типы встреч: создание, редактирование, длительность только из списка, существующие записи не меняются после правки длительности.
4. **Бэкенд: API (интеграционные тесты).** Каждый эндпоинт проверяется через HTTP: успешные ответы, ошибки валидации (`400`), конфликт (`409`), запись или тип встречи не найдены (`404`), чужой токен (`403`). Ответы сверяются со схемой из OpenAPI-спецификации.
5. **Бэкенд: одновременные запросы.** Несколько параллельных запросов на одно и то же или пересекающееся время — успешно проходит ровно один, остальные получают `409`.
6. **Фронтенд: компоненты.** Календарь (14 дней, счётчики свободных слотов, неактивные выходные и прошедшие дни), список слотов, форма записи (валидация имени и email), экран подтверждения с копированием ссылки, форма создания и редактирования типа встречи, список встреч владельца с отменой, страница записи гостя с отменой. Запросы к API подменяются моками.
7. **End-to-end.** Сценарии в браузере на запущенном приложении:
   - владелец создаёт и редактирует тип встречи;
   - гость записывается, и запись появляется у владельца;
   - второй гость не может занять то же время;
   - гость отменяет запись по ссылке, и время снова свободно;
   - гость меняет время записи по ссылке, и владелец видит новое время;
   - владелец отменяет запись из своего списка;
   - в гостевом интерфейсе нет ссылок на `/admin`.
8. **Docker.** Образ собирается, контейнер запускается, приложение отвечает на health-check, после чего на контейнере прогоняются e2e-тесты.

### Требования

- Покрытие кода бэкенда и фронтенда — не ниже 80 %, доменной логики (слоты, пересечения, отмена) — 100 %.
- Все проверки, включая e2e в браузере против настоящего сервера, запускаются одной командой `mise run check` локально и автоматически в CI на каждый push.
- Тесты не зависят от текущей даты: время в них фиксируется.

## Установка

Есть два способа запустить проект: для разработки через mise или готовым контейнером через Docker. Для Docker больше ничего ставить не нужно.

### Для разработки

Нужен только [mise](https://mise.jdx.dev/getting-started.html): он сам поставит Node.js и остальные инструменты нужных версий.

```bash
git clone https://github.com/KTelyuk/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install        # Node.js, hk, pitchfork, линтеры; затем npm ci
mise run install    # npm ci и git-хуки hk
npx playwright install chromium webkit   # браузеры для e2e-тестов
mise run dev        # бэкенд и фронтенд в фоне
```

Приложение откроется на http://localhost:5173, раздел владельца — http://localhost:5173/admin. Бэкенд стартует с тремя заготовленными типами встреч. Остановить серверы: `mise daemons stop`.

Основные команды:

| Команда                                     | Что делает                                                                                                        |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `mise run dev`                              | Запускает бэкенд (http://localhost:3000) с заготовленными типами встреч и фронтенд (http://localhost:5173) в фоне |
| `mise daemons status` / `mise daemons stop` | Состояние и остановка dev-серверов                                                                                |
| `mise run check`                            | Все проверки: сгенерированный код, линтеры, типы, тесты, e2e (то же, что в CI)                                    |
| `mise run lint` / `mise run format`         | Линтеры / автоисправление                                                                                         |
| `mise run test`                             | Тесты                                                                                                             |
| `mise run generate`                         | TypeSpec → OpenAPI → SDK фронтенда и типы бэкенда                                                                 |
| `mise run build`                            | Сборка фронтенда                                                                                                  |
| `mise run e2e`                              | Собирает фронтенд и прогоняет e2e-тесты Playwright (сервер поднимается сам)                                       |

Коммиты пишутся по [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`…), формат проверяет git-хук.

### В Docker

Нужен только [Docker](https://docs.docker.com/get-docker/). Образ сам генерирует SDK из контракта, собирает фронтенд и ставит продакшен-зависимости бэкенда.

```bash
git clone https://github.com/KTelyuk/ai-for-developers-project-387.git
cd ai-for-developers-project-387
docker build --tag call-calendar .
docker run --rm --init --name call-calendar --publish 3000:3000 call-calendar
```

Приложение откроется на http://localhost:3000, раздел владельца — http://localhost:3000/admin. Проверка работоспособности: `curl http://localhost:3000/api/health` возвращает `{"status":"ok"}`, а `docker ps` через несколько секунд показывает контейнер как `healthy`.

- Порт меняется переменной `PORT`: `docker run --rm --init --env PORT=8080 --publish 8080:8080 call-calendar`.
- В контейнере нет заготовленных типов встреч: данные хранятся в памяти и пустые при каждом запуске. Создайте тип встречи в `/admin`.
- Остановить контейнер: `Ctrl+C` (работает благодаря `--init`) или `docker stop call-calendar` из другого терминала.

Те же команды выполняет CI в job `docker`: собирает образ, запускает контейнер, ждёт health-check и прогоняет e2e против него.

### MCP для ИИ-агента

В [`.mcp.json`](.mcp.json) лежит проектная конфигурация MCP для Claude Code: сервер [Render MCP](https://render.com/docs/mcp-server), через который агент создаёт сервис, смотрит деплои, логи и переменные окружения. Токена в файле нет: Claude Code подставляет его из переменной окружения `RENDER_API_KEY`.

1. Создайте API-ключ в Render: **Account Settings → API Keys → Create API Key**.
2. Задайте переменную окружения `RENDER_API_KEY` с этим ключом:
   - macOS / Linux: `export RENDER_API_KEY=...` в `~/.zshrc` или `~/.bashrc`;
   - Windows (PowerShell): `[Environment]::SetEnvironmentVariable('RENDER_API_KEY', '...', 'User')`.
3. Перезапустите Claude Code и подтвердите подключение сервера `render` из `.mcp.json`.

Ключ даёт доступ ко всему workspace Render: не вписывайте его в `.mcp.json` и не коммитьте.

### Путь обращения

1. Человек открывает issue с потребностью своими словами. Автотриаж разбирает его и задаёт вопросы.
2. Человек отвечает и при необходимости зовёт `@claude разбери обращение по скиллу triage …` ещё раз.
3. `@claude запусти скилл to-spec` публикует спецификацию отдельным issue с метками `spec` и `ready-for-agent` и ссылкой на обращение.
4. `@claude запусти скилл to-tickets` предлагает разбиение, а после подтверждения публикует тикеты: подзадачи спецификации с меткой `ready-for-agent` и нативными зависимостями.
5. Человек подтверждает спецификацию и тикеты комментарием в исходном обращении. `implement-spec` берёт задание из спецификации и тикетов, а PR реализации ссылается на этот комментарий.
6. PR заполняется по шаблону [`.github/pull_request_template.md`](.github/pull_request_template.md): ссылки, проверки с SHA, риск, откат. CI и авторевью запускаются сами. Человек разбирает замечания и передаёт подтверждённые агенту командой `@claude` в общем комментарии или в комментарии к строке diff: комментарий авторевью сам исправлений не запускает. Правки приходят новыми коммитами в ту же ветку, CI и авторевью проверяют новую версию.
7. Человек сверяет поведение со спецификацией, фиксирует решение о мерже комментарием и сливает PR через squash.

Правила публикации — в [`docs/agents/issue-tracker.md`](docs/agents/issue-tracker.md). Пример: обращение [#13](https://github.com/KTelyuk/ai-for-developers-project-387/issues/13), спецификация [#15](https://github.com/KTelyuk/ai-for-developers-project-387/issues/15), тикеты #16–#19.

### Скиллы и настройки на раннере

Раннер начинает с чистого окружения, но всё нужное агенту лежит в репозитории и приходит с `actions/checkout`:

- скиллы проекта — в [`.claude/skills/`](.claude/skills/); глобальных скиллов проект не использует. Рабочий процесс: `to-spec` (спецификация), `to-tickets` (тикеты), `implement-spec` (реализация), а также `implement`, `triage`, `wayfinder`. Остальные: `tdd`, `diagnosing-bugs`, `code-review`, `codebase-design`, `domain-modeling`, `improve-codebase-architecture`, `grilling`, `grill-me`, `grill-with-docs`, `to-questionnaire`, `pr`, `prototype`, `research`, `retro`, `handoff`, `teach`, `wait-what`, `wizard`, `writing-for-agents`, `ask-matt`, `setup-matt-pocock-skills`;
- запуск скиллов: у `to-spec`, `to-tickets`, `implement-spec` и ещё у 13 скиллов в `SKILL.md` стоит `disable-model-invocation: true`: модель не выбирает их сама, их запускает человек. Локально это команда `/to-spec`, в GitHub — прямая просьба в комментарии: `@claude запусти скилл to-spec …`. Воркфлоу через `--append-system-prompt` объясняет агенту, что такая просьба доверенного участника и есть ручной вызов: агент читает `SKILL.md` и выполняет его шаги, а вопросы, которые скилл велит задать, задаёт комментарием и ждёт следующего вызова. Скиллы без флага (`tdd`, `code-review`, `research`, `pr` и др.) агент вызывает через `Skill` сам;
- правила и команды — в [`AGENTS.md`](AGENTS.md) (подключён из `CLAUDE.md`). Все проверки запускает одна команда: `mise run check` (сверка сгенерированного кода, линтеры, типы, тесты с покрытием, e2e). Её же вызывают CI и pre-push хук; для e2e нужны браузеры: `npx playwright install chromium webkit`;
- трекер — GitHub Issues этого репозитория, настройки — в [`docs/agents/`](docs/agents/). `docs/spec.md` описывает сервис целиком, спецификация новой доработки — отдельный issue с меткой `spec`. Агент работает с issues через `gh`, токен приложения action передаёт в `GH_TOKEN`; метки триажа: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. Issue закрывает коммит с `(#N)` в заголовке и `Closes #N` в теле PR. Создавать и править issues агенту разрешено (`gh issue …`): этого требуют `to-spec` и `to-tickets`.

### Доступ и безопасность

- **Кто запускает.** Условие `if` пропускает работу, только если в комментарии есть `@claude`, автор — `OWNER`, `MEMBER` или `COLLABORATOR`, и он не бот. Action дополнительно проверяет, что у автора есть право записи, и по умолчанию не реагирует на ботов, поэтому агент не отвечает сам себе.
- **Кто попадает в автотриаж.** `triage.yml` запускается, только если автор issue — `OWNER`, `MEMBER` или `COLLABORATOR` и не бот, а на issue нет меток `spec` и `ready-for-agent`. Спецификации и тикеты, которые создали `to-spec` и `to-tickets`, эти метки получают при создании, поэтому повторно не разбираются. В `prompt` передаётся только номер issue: текст обращения агент читает сам через `gh`, и чужой текст не становится инструкцией. Агенту разрешены только чтение кода и `gh issue view/list/comment/edit`, `gh label list`; код и ветки он не меняет, а `ready-for-agent`, `ready-for-human` и `wontfix` оставляет человеку.
- **Повторы.** `types: [created]`: правка комментария агента заново не запускает. Автотриаж срабатывает только на `opened`, правка issue его не перезапускает.
- **Форки.** `pull_request_target` не используется, `allow_fork_prs: 'false'`: недоверенные PR из форков не получают ни секрет, ни запуск агента. Тесты на ветке агент запускает только по команде участника с правом записи.
- **Права.** Воркфлоу получает только чтение (`contents`, `issues`, `pull-requests`, `actions`) и `id-token: write`, чтобы обменять OIDC-токен на короткоживущий токен Claude GitHub App. Комментарии и push агент делает правами приложения, поэтому у `actions/checkout` стоит `persist-credentials: false`. В `--allowedTools` перечислены только инструменты, нужные скиллам: `Skill` и субагенты, чтение и правка файлов, `gh issue …`, чтение PR через `gh pr view/diff/list/checks`, `mise run lint/format/typecheck/test/build/generate/check-generated`, `npm test` и git-команды для веток, коммитов и push. Для этого воркфлоу ставит инструменты проекта через `jdx/mise-action`. Остальные команды (например `gh api`, `rm`, сетевые запросы) не разрешены. e2e агент не запускает: их прогоняет CI на каждый push.
- **Авторевью.** `review.yml` запускается на `pull_request` только для веток этого репозитория (PR из fork не получают секрет, `pull_request_target` не используется) и только если автор PR — `OWNER`, `MEMBER`, `COLLABORATOR` или приложение `claude[bot]`, которое открывает PR `implement-spec`. Общий фильтр по типу `Bot` не подходит: он отключил бы ревью PR агента. Черновики не ревьюятся, ревью начинается на `ready_for_review`. Модель запускается обычным CLI `claude -p`, а не через `claude-code-action`: action проверяет права отправителя события и на PR приложения остановил бы ревью. Задание с моделью получает только чтение (`contents`, `issues`, `pull-requests`, `actions`, `checks`, `statuses`), без `id-token`, и инструменты `Read`, `Glob`, `Grep` только внутри checkout и подготовленного контекста, а также `gh pr view/diff/checks` и `gh issue view`; запись файлов запрещена. `git` модели недоступен: `git diff --no-index` читает любой файл, а `git diff --output` пишет файл. Diff, список коммитов и критерии ревью готовит отдельный шаг до запуска модели. Модель читает недоверенный текст PR и issues, а в её окружении лежит токен подписки, поэтому `/proc`, `/sys` и `/etc` закрыты явно, а ответ, в котором найден токен, не публикуется. Критерии (`REVIEW.md`, `AGENTS.md`, `docs/agents/issue-tracker.md`) берутся из базовой ветки, чтобы автор PR не менял правила своей проверки; из head — только если в базе файла ещё нет. Комментарий публикует отдельное задание `publish` без модели с `pull-requests: write`; в комментарий идёт текст отчёта с первого заголовка, промежуточные реплики модели отбрасываются. Ревью проверяет head SHA PR, а не merge-коммит, и до 12 минут ждёт, пока появятся и завершатся все проверки CI из `REQUIRED_CHECKS` (`check`, `docker`, `build`, `e2e-head`, `commits`); при новом задании в CI его имя добавляют туда. `concurrency` по номеру PR с `cancel-in-progress: true` отменяет ревью устаревшей версии, а `timeout-minutes: 25` и `--max-turns 40` ограничивают прогон. Комментарий авторевью пишет `github-actions[bot]`, поэтому `claude.yml` на него не реагирует.
- **Предел запусков на PR.** Агента на одном PR допускают не больше 3 раз. Задание `gate` без модели и секретов выполняется до задания `claude`: с `GITHUB_TOKEN` и `actions: read` оно читает историю прогонов `claude.yml` с момента открытия PR, выбирает прогоны с названием `claude PR #N` (`run-name` строится из события, а не из текста комментария) и считает попытки, в которых gate выполнил шаг `Admit run`. В счёт идут и `cancelled`, и `timed_out`, и каждая попытка Re-run (`run_attempt`), а общие комментарии (`issue_comment`) и комментарии к строкам diff (`pull_request_review_comment`) расходуют один бюджет. Счётчик — сама история Actions, комментарии PR его не меняют. «Re-run failed jobs» не перезапускает gate, поэтому агент в такой попытке не запускается: повтор — только через «Re-run all jobs», и он считается. После исчерпания бюджета команда `@claude` завершается без вызова модели. Продолжить работу после исчерпания бюджета решает человек: например, сам дописывает правки или открывает новый PR из той же ветки.
- **Удаление прогонов.** У приложения Claude есть `actions: write` и `workflows: write`, поэтому его токеном можно удалить прогон из истории. Агенту такие команды не разрешены, но gate на это не полагается: номера прогонов воркфлоу идут подряд и не переиспользуются, и gate проверяет, что от последнего прогона перед открытием PR до текущего нет пропусков. Если пропуск есть, gate закрывается (`limit_exhausted`, нужен человек). Комментарий к строке diff запускает `claude.yml` из ветки PR, поэтому правка воркфлоу в PR обошла бы gate: агенту запрещены `Edit` и `Write` в `.github/workflows/`, а правки воркфлоу в PR проверяет человек.
- **Предел на issue.** На обычных issue предел не действует: там идёт разговор (триаж, `to-spec`, `to-tickets`), и каждый ответ на вопрос агента — новый вызов. Код агент меняет и тратит основной бюджет в PR, а один прогон на issue ограничивают таймаут и `--max-turns`.
- **Отчёт о сбое.** Задание `report` без модели (`if: always()`, свой `timeout-minutes: 5`, поэтому успевает и после таймаута агента) публикует комментарий от `github-actions[bot]`, если агент не отработал: причина `limit_exhausted` (бюджет исчерпан или повтор без gate), `timeout` (задание агента остановлено по `timeout-minutes`), `infra` (сбой gate, нет секрета, сбой checkout или установки инструментов) или `agent_failed` (ошибка на шаге агента или отмена), число допущенных запусков, последний head SHA, ссылку на лог попытки и статус «нужен человек». `claude.yml` на комментарии ботов не реагирует.
- **Проверка на head SHA.** `e2e-head.yml` запускается на `pull_request` без секретов и только с `contents: read`, делает checkout `github.event.pull_request.head.sha`, сверяет его с `git rev-parse HEAD` и прогоняет e2e с `E2E_EVIDENCE=1`: в `e2e/playwright.config.ts` это включает `trace: 'on'` и `screenshot: 'on'`. Артефакт `e2e-<sha>` хранится 14 дней.
- **Формат коммитов в CI.** `commits.yml` запускается на `pull_request` без секретов, с `contents: read`. Заголовок PR и сообщения коммитов передаются через `env` и файлы, а не подставляются в скрипт. Событие `edited` перезапускает проверку после правки заголовка. Защита появилась после того, как агент на раннере коммитит без хука hk: правило формата теперь проверяет CI, а не только локальный хук.
- **Ключ.** Токен лежит только в Settings → Secrets and variables → Actions под именем `CLAUDE_CODE_OAUTH_TOKEN`.
- **Токен релизов.** `release-please.yml` создаёт и обновляет release-PR fine-grained токеном владельца из секрета `RELEASE_PLEASE_TOKEN`: доступ только к этому репозиторию, права `Contents` и `Pull requests` на запись. Push и PR через `GITHUB_TOKEN` не запускают `ci.yml`, а `pull_request`-проверки на PR от `github-actions[bot]` ждут ручного одобрения, поэтому release-PR не проходил обязательные проверки `main`. С токеном владельца автор release-PR — владелец, проверки и авторевью идут как на обычном PR. Если секрета нет, прогон падает на шаге `Require release token`, а не откатывается молча на `GITHUB_TOKEN`.
- **Остановка.** `timeout-minutes: 40` и `--max-turns 80` ограничивают один прогон, у автотриажа — `timeout-minutes: 15` и `--max-turns 30`. `concurrency` по номеру issue или PR в обоих воркфлоу не даёт запускать агента параллельно в одном обсуждении. На PR, кроме того, действует предел в 3 запуска агента. Текущий прогон останавливает **Cancel workflow** в Actions, будущие — **Disable workflow**; при необходимости токен отзывают в настройках аккаунта Claude.

### Подключение

1. Установить [Claude GitHub App](https://github.com/apps/claude) на репозиторий.
2. Выполнить `claude setup-token` и сохранить токен в секрет репозитория `CLAUDE_CODE_OAUTH_TOKEN`.
3. Создать fine-grained токен только на этот репозиторий с правами `Contents` и `Pull requests` на запись и сохранить его в секрет `RELEASE_PLEASE_TOKEN` для release-please.
4. Написать в issue `@claude explain this issue` и проверить ответ и прогон в Actions.
5. Задать переменную репозитория `APP_URL` (Settings → Secrets and variables → Actions → Variables) с адресом приложения для аудита скорости.

## Аудит скорости по расписанию

[`audit.yml`](.github/workflows/audit.yml) раз в сутки замеряет скорость гостевых страниц и превращает новую находку в задачу. Тот же файл запускается вручную кнопкой **Run workflow** во вкладке [Actions](https://github.com/KTelyuk/ai-for-developers-project-387/actions/workflows/audit.yml).

### Как устроен

1. **Запуск.** `schedule` с `cron: '17 3 * * *'` и `timezone: Asia/Almaty`, то есть раз в сутки в 03:17 по Алматы, в часовом поясе приложения. `workflow_dispatch` принимает `source`: `live` — аудит настоящего приложения, `sample` — учебный отчёт. По расписанию всегда идёт `live`.
2. **Ограничения.** `timeout-minutes: 30`, `concurrency: audit` без отмены: второй аудит ждёт первый, иначе два агента могли бы завести одну задачу дважды.
3. **Сбор данных без модели.** Сначала прогрев: бесплатный Render засыпает, поэтому шаг до 12 раз опрашивает `$APP_URL/api/health`. Без прогрева Lighthouse замерил бы холодный старт сервиса. Node берётся из `mise.toml` через `jdx/mise-action`: `@lhci/cli` требует Node 22.19 или новее. Затем [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci) (`@lhci/cli`, версия закреплена в [`.github/audit/package.json`](.github/audit/package.json) с lock-файлом вне npm workspaces) делает по 3 прогона страниц `/` и `/book` с мобильным профилем по умолчанию. `/admin` не проверяется: это раздел владельца.
4. **Сводка.** [`summarize.mjs`](.github/audit/summarize.mjs) берёт медианный прогон каждой страницы и пишет короткий `summary.json`: оценки, пять основных метрик и находки. Находка — метрика в красной зоне Lighthouse (`score < 0.5`) с ключом `audit:<метрика>@<путь>` и до трёх возможностей оптимизации с экономией от 300 мс. Если приложение не ответило, Lighthouse не сохранил отчёт или не замерил ни одной страницы, статус `no_data`; если не замерена часть страниц — `partial`: это не значит, что проблем нет. Агент пишет об этом в журнал, а последний шаг роняет прогон, чтобы сломанный аудит пришёл уведомлением, а не выглядел зелёным.
5. **Результат.** Полный отчёт и сводка сохраняются артефактом `audit-<source>-<run_id>` на 30 дней. Отчёты пишутся в `$RUNNER_TEMP`, вне рабочего дерева, а `.lighthouseci/` в `.gitignore`: в коммиты они не попадают.
6. **Агент.** `claude-code-action` получает инструкцию в `prompt`: путь к сводке, источник, ссылку на прогон и SHA `main`. Агент:
   - для каждой находки ищет issue с меткой `audit`, включая закрытые, по строке `audit-key: <ключ>` в тексте;
   - создаёт задачу только по новой находке: проблема, предлагаемое действие, связь с отчётом. Цифры переносятся в текст, потому что артефакт временный. Ставятся метки `audit` и `needs-triage`;
   - если задача уже есть, новую не создаёт и в неё не пишет. Если такая задача закрыта, в журнале появляется пометка «находка снова появилась после закрытия #N»;
   - оставляет один комментарий о запуске в issue «Аудит скорости: журнал запусков» (метка `audit-log`): оценки страниц, по каждой находке «новая задача» или «уже есть», либо «Находок нет», либо «Данных нет».
7. **Права.** `GITHUB_TOKEN` получает только `contents: read` и `issues: read`. Задачи и комментарии агент создаёт токеном Claude GitHub App через `id-token: write`. В `--allowedTools` только `Read` и `gh issue list/view/create/comment`. Файлы, `git`, ветки и PR агенту недоступны: этот сценарий их не меняет.
8. **Учебная находка.** `source=sample` подставляет [`.github/audit/sample-summary.json`](.github/audit/sample-summary.json). Там явно помеченная учебная находка с отдельным ключом `audit-sample:…`, чтобы она не совпала с настоящей. Задача по ней получает префикс `[Учебный]`, метку `учебный` и первую строку о том, что это не подтверждённый дефект.

Новая задача — входящее обращение. Брать ли её в работу, решает человек, дальше идёт обычный путь: спецификация и тикеты. Автотриаж такие issue не разбирает, потому что их автор — бот.

### Когда ждать запуск

Расписание работает, только если файл лежит в `main` и воркфлоу включён. GitHub может задержать запуск по расписанию или пропустить его, а в публичном репозитории отключает расписание после 60 дней без активности. Если запуск не состоялся, проверьте, что `audit.yml` есть в `main`, воркфлоу не выключен (Actions → audit), cron и [статус GitHub Actions](https://www.githubstatus.com/). Сам сценарий проверяется ручным запуском, не дожидаясь расписания.

## План реализации

Работа идёт циклом: обсуждение → спецификация → тикеты → реализация → проверка. Каждый этап заканчивается коммитом; этап готов, когда все его проверки проходят.

### Этап 0. Каркас и агентная среда ✅

- Монорепозиторий на npm workspaces: `typespec`, `backend`, `frontend`.
- Бэкенд по getting started Fastify, фронтенд через `create-vite` и `shadcn init`.
- Проверка цепочки TypeSpec → OpenAPI → SDK на эндпоинте `GET /api/health`.
- Дымовой тест на Vitest: приложение поднимается и отвечает на `/api/health`.
- Oxlint и oxfmt, проверка типов, git-хуки hk, jactionlint, agnix.
- `mise.toml`: версии инструментов, задачи, daemons для dev-серверов. `mise run check` — все проверки одной командой.
- CI в GitHub Actions на каждый push вызывает `mise run check`. Файл `hexlet-check.yml` не трогаем.
- Conventional Commits, AGENTS.md (через `/init`, сокращён до команд, устройства и правил).

**Готово, когда:** `mise run check` проходит локально и в CI.

### Этап 1. Спецификация ✅

- `docs/spec.md`: роли, сценарии, параметры расписания, правила пересечений и отмены, коды ответов — на основе разделов «Сценарий» и «Правила и ограничения».
- Модели данных:
  - `EventType`: `id`, `title`, `description`, `durationMinutes` (15 | 30 | 45 | 60);
  - `Booking`: `id`, `eventTypeId`, `guestName`, `guestEmail`, `startAt`, `endAt`, `createdAt`; `cancelToken` хранится на сервере и отдаётся гостю один раз при создании;
  - `Slot`: `startAt`, `endAt`.
- Таблица эндпоинтов (см. этап 2).
- Разбивка спецификации на тикеты в [GitHub Issues](https://github.com/KTelyuk/ai-for-developers-project-386/issues) — по одному issue на тикет: что сделать, критерии приёмки, блокирующие тикеты.

**Готово, когда:** спецификация и тикеты закоммичены, открытых вопросов нет.

### Этап 3. Бэкенд ✅

Тикеты по порядку:

1. **Сервер.** Fastify, `fastify-openapi-glue` с контрактом, `/api/health`, единый обработчик ошибок, конфиг из переменных окружения (`PORT`).
2. **Хранилище в памяти.** Репозитории типов встреч и записей с методами, которые потом можно заменить на базу.
3. **Типы встреч.** Список, получение, создание, редактирование.
4. **Расчёт слотов.** Чистые функции: рабочие дни, часы 09:00–18:00 по Алматы, шаг 15 минут, окно 14 дней, исключение прошедших и занятых слотов. Текущее время передаётся параметром, чтобы тесты не зависели от даты.
5. **Бронирование.** Проверка пересечения и сохранение — одной синхронной операцией. Генерация токена отмены.
6. **Отмена гостем и владельцем.** Проверка токена, запрет отмены начавшейся встречи, удаление записи.
